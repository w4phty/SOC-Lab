## Splunk alerts


For this lab, we create reports containing splunk requests, that will filter and search through the collected logs, and register any matching alert in the **siem_alerts** index.

Each alert contains the following mandatory fields: **alert_name, rule_id, severity, mitre_technique, platform, datasource, sigma_id formatted_time**. 

And optional fields, according to the original datasource: **hostname, user, event_code, src_ip, dest_ip, dest_port, executable, process_name, parent_executable, command_line, file_path, alert_signature, sourcetype**.

The version of Splunk used is the Free version. Therefore, the option that allows a user to create scheduled alerts is unavailable, this is why reports are used instead. The reports created are divided as follows: linux, windows, network, and a global report. They can be run with a custom time range, that will be set so that we collect the logs corresponding to each studied attack scenario, in order to avoid creating duplicates. 

It is also worth noting that in the lab, the datasource of the created alerts is `stash` by default, but in a production environment we would have changed this to collect data in a real datasource.


### Automation script

Writing splunk requests based on sigma rules is very repetitive, this is why I decided to create a python script to automate it. This is a custom script that covers any sigma syntax useful for this lab. 

It is made of 2 main components:
- [custom_sigma2splunk.py](./custom_sigma2splunk.py) : turns each sigma rule into an spl request
- [splunk_report_generator.py](./splunk_report_generator.py) : concatenates the spl requests sent by custom_sigma2splunk.py, and creates the reports that can be directly used in Splunk

Usage: 
```
python ./splunk_report_generator.py
```

Some of the advantages of using the automation script to create the reports are:
- Time spared concerning the creation and updates of the reports
- Increases the quality of the reports and helps avoiding human mistakes
